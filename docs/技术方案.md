## 0. 核心结论（先看这 9 条）

1. **规则层真正的病根不是 UI，而是"名称与语义不符 + 没有优先级 + 没有边界校验"。** `pathReplace` 实际执行的是"整条 path 覆盖"（`sw.js:18`），不是前缀替换，"自动继承 query"的提示只对 query 成立，对路径后缀不成立。
2. **要保留通配捕获的后缀，`transform.path` 做不到，必须用 `regexFilter` + `redirect.regexSubstitution`（`\1` 回填）。** DNR 的 redirect 有三种形态（`url` / `transform` / `regexSubstitution`），能力边界互不相同，当前只用了前两种。
3. **现有全部 DNR 规则 `priority: 1`（`sw.js:35`），同优先级由浏览器按 action 类型排序，同一请求命中多条 redirect 时结果不受你控制。**
4. **一条非法规则会让 `updateDynamicRules` 整次调用失败（原子性），而 `syncRules` 没有 try/catch（`sw.js:48-59`），结果是"一条写错，全部代理失效，UI 无任何提示"。** 这是当前最危险的工程缺陷。
5. **Mock 结论：DNR 无法合成响应体，`data:`/`blob:` 也不是合法 redirect 目标。** 不采用 `chrome.debugger`（权限、黄条、审核代价过高），最终方案是 **MAIN world 注入拦截 `fetch`/`XMLHttpRequest`**，并把能力边界写进产品文案：只覆盖"页面脚本发起的 fetch/XHR"，不覆盖 `<img>`、iframe、Worker、Service Worker。同一条规则在 mock 与转发之间二选一，**mock 规则不再编译进 DNR**。
6. **抓包面板当前每 800ms 把整页缓冲区 `JSON.stringify` 一次（`devtools-panel.js:32-42`、`devtools-panel.js:118`）。** 2000 帧 × 8000 字符上限 = 单次最多约 16M 字符（中文场景更大），在页面主线程串行化后回传，属于"用最贵的方式传最少的新数据"。必须改为增量游标 + 虚拟滚动 + 主从布局。
7. **WS 数据侧缺的不是分组，而是"可对齐的会话标识"。** `ws-1` 每页面重置（`ws-hook-source.js:54`），导出不带 `seq`、不带 `sessionId`、单帧截断无标记，多份导出合并必然撞 id；导出 schema 需要 v2（旧字段全部保留）。
8. **上架最可能被卡的两点：①"单一用途"（HTTP 转发 + WS 抓包是两件事）②`<all_urls>` 广域主机权限 + `declarativeNetRequest` 的申请理由。** 次高风险是把 `fetch` 打包文件再 `eval` 注入（`devtools-panel.js:24-30`）被误判为远程代码。
9. **请求头配置可以并入现有规则模型，不需要第二套规则。** DNR 的 `redirect` 与 `modifyHeaders` 分属两个评估阶段、可同时生效；但 `action.type` 是单值枚举，所以一条用户规则要拆成 1–2 条 DNR 规则（redirect 用 `1000+i`、请求头用 `2000+i`、两者同 priority）。**WebSocket 握手头无法配置**，该能力只对 HTTP(S) 生效。

### 1.2 代理规则语义问题（P0）

| 编号 | 现象 | 证据 | 影响 |
|---|---|---|---|
| P-01 | `pathReplace` 名为"路径替换"，实为"整条 path 覆盖" | `popup.html:35` 文案 vs `sw.js:18` `transform:{path}` | 用户填 `/api/*` → 目标 `/proxy/api`，`/api/123` 变成 `/proxy/api`，`123` 丢失 |
| P-02 | 通配 `*` 只参与匹配，不参与重写 | `popup.html:22` 提示"支持 `*` 通配" vs `sw.js` 无捕获逻辑 | 通配规则必然丢后缀，规则越"通用"错得越狠 |
| P-03 | 路径无边界，`/api` 会命中 `/apix`、`/api-v2` | `sw.js:38` 只有起始锚 `\|`，无结束边界 | 误伤同前缀接口 |
| P-04 | `urlFilter` 默认大小写不敏感 | DNR 默认 `isUrlFilterCaseSensitive=false`，代码未设置 | `/API` 与 `/api` 被视为同一规则，排查困难 |
| P-05 | query 语义不对称：路径替换保留、完整 URL 丢弃 | `sw.js:15` 整体替换 `redirect.url`；`sw.js:18` 仅传 `path` | 用户以为两种模式都"继承 query"，切到 fullUrl 后参数全丢 |
| P-06 | 路径替换改不了 host/port/scheme | `transform` 只设置 `path`（`sw.js:18`） | 想指向测试域必须用 fullUrl，UI 未说明边界 |
| P-07 | `pathPattern` 若含 `?` 或 `#`，匹配语义破碎 | `sw.js:38` 直接拼接进 `urlFilter` | query 顺序一变就不命中，或命中后被 `transform` 覆盖 |
| P-08 | 所有规则 `priority: 1` | `sw.js:35` | 多规则命中时不可控；DNR 同优先级按 action 类型排序（allow > allowAllRequests > block > upgradeScheme > redirect > modifyHeaders），redirect 之间无定义顺序 |
| P-09 | 每条配置生成 http + https 两条规则 | `sw.js:31-42` | 规则数翻倍；`MAX_RULE_ID=500`（`sw.js:10`）实际只支持约 250 条配置，超出后静默 `break`（`sw.js:32`）无提示 |
| P-10 | 规则同时覆盖 `main_frame` | `sw.js:9` | 一条路径规则可能把整页导航改走，风险与收益完全不对称 |
| P-11 | 声明了 `websocket` 资源类型，但 redirect 对 WS 握手不生效 | `sw.js:9` | 造成"WS 也被代理"的错觉；Chrome webRequest 文档明确 "Redirects are not supported for WebSocket requests" |
| P-12 | `type=mock` 在编译期直接返回 null | `sw.js:12-13` | 规则被静默跳过，但 popup 仍可保存、仍显示"启用"，属于"假启用" |
| P-13 | 无优先级、无规则名、无分组、无导入导出 | `popup.js:59-68` 字段集合 | 规则过 10 条后只能靠肉眼辨认 |
| P-14 | 规则自环无检测 | 无任何目标与源比对逻辑 | `/→/` 或目标再次命中自身时触发浏览器 5 跳上限，表现为 `ERR_TOO_MANY_REDIRECTS`，用户无从判断 |

## 2. 目标与非目标

### 2.1 目标

1. **可解释**：用户输入一个 URL，能立刻看到"哪条规则命中、最终跳到哪里、为什么没命中"。
2. **可校验**：非法配置在保存前被拦住，且错误定位到字段；任何一条坏规则都不能影响其它规则生效。
3. **语义收敛**：一个字段只有一种含义，UI 文案与 DNR 行为逐字对齐（尤其 query 与通配后缀）。
4. **Mock 真可用**：范围写清楚、命中率可预期、不会"显示启用但什么都不做"。
5. **规模可用**：配置页支撑 100+ 条规则；面板支撑 500+ 连接、2000 帧而不卡。
6. **可迁移**：规则与抓包数据都有稳定 schema，可导入导出、可被脚本消费。
7. **可上架**：满足 Chrome Web Store 与 Edge Add-ons 的最小权限、单一用途、无远程代码要求。

### 2.2 明确不做

| 不做 | 原因 |
|---|---|
| 读取/修改请求体、伪造任意响应（走 `chrome.debugger`） | `debugger` 权限警告强、与 DevTools 抢附着、审核成本最高，收益不匹配 |
| 修改或重放 WebSocket 消息 | 浏览器扩展无法在后台劫持已建立的 WS；需要 MITM 代理，超出产品边界 |
| HTTPS 证书解密 / 系统级 MITM | 与"轻量联调工具"定位冲突，安全与合规成本不可接受 |
| 云端规则同步、团队协作 | v1 不做；先把本地模型与导入导出做稳 |
| 多标签页流量聚合 | DevTools 面板天然只服务一个被检查页面，强行聚合会引入新的会话模型 |
| 引入构建工具链 | 当前"免构建、可解压加载"是优势；新代码用原生 ES Module 即可 |
| Firefox / Safari 适配 | 本次只对齐 Chrome / Edge（两者 DNR 行为一致） |

## 3. 模块 A：代理配置页重设计

### 3.1 先定容器：popup 只做"状态卡"，完整配置进 options 页

现状把"列表 + 新增表单"塞进 520px 弹窗（`popup.html:2`），规则一多必然挤压。结论：

| 容器 | 职责 | 理由 |
|---|---|---|
| `popup.html`（约 360×420） | 全局开关、已启用条数、最近命中/最近修改的 3 条、**打开完整配置**、**打开抓包面板说明** | 点图标的高频动作是"确认开没开"，不是"编辑第 12 条规则" |
| `options.html`（整页，`options_ui.open_in_tab`） | 规则列表、搜索过滤、详情抽屉、导入导出、诊断器 | 可自由布局、可多列、可拖拽调整、可容纳表格 |

manifest 需新增 `options_ui`（`open_in_tab: true`），popup 里用 `chrome.runtime.openOptionsPage()` 跳转。popup 与 options **共享同一份纯函数规则模块**（`rules-model.js`：校验、编译、匹配模拟），避免两份逻辑漂移。

### 3.2 信息架构：列表 + 详情抽屉（不做卡片墙）

**结论：主视图用"紧凑列表（表格）"，右侧用"详情抽屉"，不用卡片。**

理由（针对"规则数量中等、需要快速判断哪条在生效"）：

1. **可比较性**：用户的核心问题是横向对比——哪条开着、匹配什么、指向哪、最近有没有命中。表格的列对齐天然支持这种扫描；卡片把同一字段放在不同纵向位置，比较成本随条数线性上升。
2. **密度**：卡片模式下 1 条规则约占 90–120px（标题 + 两行副信息 + 操作区），10 条就超过一屏；表格 44px/行可放 14–16 条，接近"中等规模"的实际需求。
3. **上下文**：编辑用抽屉而不是新页面/新弹窗，列表仍可见，改完能立刻对比相邻规则，也避免"弹窗套弹窗"。
4. **扩展性**：批量选择、拖拽排序、列宽记忆都只在表格模型下成立。

不用"手风琴展开行"（`<details>` 式）：展开会把后续行推走，且同一时间只能看一条的字段，无法比较。

### 3.4 空态

```
还没有代理规则
把请求路径映射到测试环境，或直接返回固定 JSON。
[新建规则]   [导入规则文件]   [粘贴一个 URL 自动生成 →]
```

规则：**纯文字 + 一个主按钮 + 两个次动作 + 一行示例**，不放插画、不放插画式 SVG、不放"欢迎使用"大标题。

### 3.5 编辑态（抽屉）

抽屉内 3 段 + 1 折叠段：

1. **基本信息**：名称（可空，留空自动生成 `host path → target`）、启用、备注。
2. **匹配**：scheme（http/https/两者）、host、path、大小写敏感、资源类型（默认只勾 `xhr/fetch` 与 `other`，`main_frame` 单独一个带警示的开关）。
3. **动作**：类型三选一
   - 转发·整路径替换（`exact`，可改 host）
   - 转发·前缀替换（`prefix`，保留通配后缀，可保留/丢弃 query）
   - Mock（提示"仅对页面脚本发起的 fetch/XHR 生效"，见 4.7）
4. **高级（折叠）**：优先级（数字，默认按列表顺序自动生成）、额外排除 host、测试 URL。

交互细节：

- **未保存离开** → 拦截并提示"有未保存修改"（Esc 先关抽屉再提示）。
- **保存按钮**只在有改动且校验通过时可用；错误在字段下方 inline 显示，同时在抽屉顶部汇总"3 个问题"。
- **实时编译预览**：抽屉底部显示"将写入浏览器的规则"（只读折叠 JSON），用户能看到 `priority`、`regexFilter`、`resourceTypes` 的真实值。
- **诊断器**：输入一个示例 URL，返回"命中 / 未命中 / 被更高优先级规则覆盖"，并给出最终目标 URL（纯本地模拟，不需要任何权限）。

- **数字对齐**：命中次数、帧数、耗时一律 `font-variant-numeric: tabular-nums`，右对齐。

## 4. 模块 B：代理规则语义与规则模型（重点）

### 4.1 现有字段逐条行为

| 字段 | 用户输入 | 代码实际行为 | 证据 | 坑 |
|---|---|---|---|---|
| `host` | `192.168.1.100` | 被直接拼进 `urlFilter`：`\|https?://{host}{path}` | `sw.js:38` | 它不是"host 匹配"，是"URL 字符串前缀"；填成 `https://x` 或带端口/斜杠会静默错配；也允许子域穿透 |
| `pathPattern` | `/demo/api/sessions` | 同上，字符串前缀；`*` 是通配符 | `sw.js:38`、`popup.html:21-23` | 无路径边界；`*` 只影响"是否命中"，不影响"跳到哪" |
| `type` | `proxy` / `mock` | `proxy` 才编译；`mock` 返回 null | `sw.js:13` | mock 规则永不生效，但 UI 显示启用 |
| `proxyMode` | `pathReplace` / `fullUrl` | 决定 redirect 形态 | `sw.js:14-18` | 两种模式 query 语义相反，UI 只在其中一处提示 |
| `proxyPathPrefix` | `/proxy/api/sessions` | 作为 `transform.path` **整条替换** | `sw.js:18` | 名字暗示"前缀"，实际是"新路径"；通配后缀丢失 |
| `proxyTarget` | `http://xxx/xxx?a=1` | 作为 `redirect.url` **整条替换** | `sw.js:15` | 原 query 全丢；也允许非绝对地址导致规则非法 |
| `mockBody` | JSON 文本 | 不参与任何逻辑 | `popup.js:66` | 存了但没人读，形成"配置假象" |
| `enable` | `true/false` | 编译期过滤 | `sw.js:26` | 正确；但无"应用失败"状态回传 |

### 4.2 歧义与坑（按严重度）

| 编号 | 歧义/坑 | 具体说明 | 结论 |
|---|---|---|---|
| R-1 | `pathReplace` 的"替换"到底是前缀还是整路径 | UI 叫"替换后路径"（`popup.html:39`），DNR 是"new path" | 必须拆成 `exact` / `prefix` 两种模式，名字直接写在 UI 上 |
| R-2 | 通配后缀能不能保留 | `transform` 无捕获能力；`urlFilter` 的 `*` 只匹配不捕获 | 只有 `regexFilter` + `regexSubstitution(\1)` 能保留；这是唯一正确实现 |
| R-3 | query 到哪去了 | `transform` 不传 `query` → 原 query 保留；`redirect.url` → 整体替换 | 显式提供 `keepQuery`，两种模式都遵循同一套规则 |
| R-4 | `/api` 与 `/apiv2` 会不会混 | 会（无边界） | 精确模式与前缀模式都必须加尾边界；精确模式锚定整条 path |
| R-5 | 大小写 | `urlFilter` 默认不敏感 | 显式 `isUrlFilterCaseSensitive: true`，并在 UI 说明"路径区分大小写" |
| R-6 | 多条命中谁赢 | 全部 `priority:1` | 用户可见排序即优先级；编译时映射为唯一 DNR priority，禁止并列 |
| R-7 | 会不会自己跳自己 | 无检测 | 编译前做自环检测（源与目标同 host 且目标 path 前缀等于源前缀 → 拒绝）；运行时浏览器 5 跳保护是兜底不是设计 |
| R-8 | 能不能跳到 `data:` 做 mock | 不能，redirect 目标必须是 http/https 或扩展内路径 | 直接排除"用 data URL 伪造响应"这条路 |
| R-9 | 跨域会发生什么 | redirect 是浏览器发起的新请求，仍受 CORS、预检、Cookie `SameSite`、混合内容限制 | https 页面跳 http 目标会被 mixed content 拦截；目标必须回 `Access-Control-Allow-Origin`（含凭据时不能用 `*`） |
| R-10 | POST 的 body 保不保 | DNR redirect 对带 body 请求的处理需实测 | 【待验证：DNR redirect 对 POST body 与 OPTIONS 预检的行为】；文档层不承诺"body 原样转发" |
| R-11 | 为什么 `main_frame` 危险 | 整页导航会被改写，一条宽规则就能让站点打不开 | 默认不勾选；勾选需二次确认 |
| R-12 | `websocket` 覆盖是真的吗 | 不是。redirect 对 WS 握手不生效（webRequest 文档明确不支持 WS redirect） | 从默认资源类型移除；文档/UI 明确"WS 不做代理" |
| R-13 | mock 为什么不生效 | DNR 只能改请求目标，不能合成响应体；编译期直接 return null | 见 4.7 的独立方案 |
| R-14 | 一条错规则为何全灭 | `updateDynamicRules` 原子，`syncRules` 无 catch | 单规则编译 + 逐条 `addRules` 失败隔离，或整批校验后再提交 |
| R-15 | 规则 id 为什么对不上 | 每次重排 1..N | 编译顺序确定 + 持久化 `configId → dnrId` 映射 |
| R-16 | 500 上限怎么算 | 500 是自设常量，且每配置 2 条 | 用 `requestDomains` 合并 http/https 后翻倍问题消失；超限要显式报错而非 `break` |

### 4.3 规则模型（字段定义）

**两层模型**：`Rule`（用户配置，稳定 UUID）→ `CompiledRule`（DNR 规则，1..N 条，可重建）。UI 只操作 `Rule`，DNR 永远是派生物。

| 字段 | 类型 | 必填 | 默认 | 语义 | 校验 |
|---|---|---|---|---|---|
| `id` | string(uuid) | 是 | 自动 | 稳定标识，导入导出/映射/撤销都依赖 | 唯一 |
| `name` | string | 否 | 自动生成 `host path → target` | 列表主标题辅助 | ≤ 60 字符 |
| `enabled` | boolean | 是 | `true` | 是否参与编译 | — |
| `order` | number | 是 | 列表位置 | 用户可见顺序，**即优先级来源**，可拖拽 | 整数，唯一 |
| `match.scheme` | `"http"\|"https"\|"both"` | 是 | `both` | 协议范围 | — |
| `match.host` | string | 是 | — | 精确域名，或 `*.example.com`（**只允许最左一段为通配**） | 合法 host；不含 scheme/端口/斜杠；不得为纯 `*` |
| `match.path` | string | 是 | — | 以 `/` 开头；`*` 只能是**尾部通配**（`/api/*`）或整段通配（`/api/*/detail`），不支持正则 | 以 `/` 开头；不含 `?`/`#`；不含连续 `**` |
| `match.caseSensitive` | boolean | 否 | `true` | 路径是否区分大小写 | — |
| `match.excludeHosts` | string[] | 否 | `[]` | 排除的 host（避免自环/误伤） | 合法 host |
| `action.kind` | `"redirect-exact"\|"redirect-prefix"\|"redirect-url"\|"mock"\|"headers-only"` | 是 | `redirect-prefix` | 动作类型；`headers-only` 为新增：只改请求头、不改向（见 4.9.1） | — |
| `action.targetPath` | string | 条件 | — | `redirect-exact`：完整新路径；`redirect-prefix`：新前缀 | 以 `/` 开头 |
| `action.targetUrl` | string | 条件 | — | `redirect-url` 的绝对地址 | `http(s)://`，可被 URL 解析 |
| `action.keepQuery` | boolean | 否 | `true` | 重定向后是否保留原 query | 与 `targetUrl` 内已有 query 冲突时提示 |
| `action.targetScheme` / `targetHost` / `targetPort` | string | 否 | 继承 | `redirect-exact` 可改 host/port/scheme（`transform` 支持） | 合法值；改 host 需用户显式展开"高级" |
| `action.headers` | `HeaderOp[]` | 否 | `[]` | 请求头修改列表；仅 `redirect-*` 与 `headers-only` 允许（详见 4.9） | ≤ 16 条；总大小 ≤ 8KB |
| `action.headers[].op` | `"set"\|"append"\|"remove"` | 是 | — | 设置 / 追加 / 删除 | `remove` 不允许带 `value` |
| `action.headers[].name` | string | 是 | — | 头名，大小写不敏感 | RFC 7230 token；禁用名单见 4.9.8 |
| `action.headers[].value` | string | 条件 | — | `set`/`append` 必填；`remove` 必须为空 | ≤ 4KB；不含 CR/LF |
| `action.mock.status` | number | 条件 | `200` | Mock HTTP 状态码 | 100–599 |
| `action.mock.headers` | object | 否 | `{"content-type":"application/json"}` | 响应头 | 键值合法；禁止 `set-cookie`（浏览器侧无法可靠生效） |
| `action.mock.body` | string | 条件 | `{}` | 响应体 | JSON 类型时必须可 `JSON.parse`；≤ 1 MB |
| `action.mock.delayMs` | number | 否 | `0` | 模拟延迟 | 0–10000 |
| `scope.resourceTypes` | enum[] | 是 | `["xmlhttprequest","other"]` | 参与匹配的资源类型 | ≥1；`main_frame` 需二次确认 |
| `scope.excludeInitiator` | string[] | 否 | `[]` | 排除发起方域 | 合法 host |
| `notes` | string | 否 | `""` | 备注（为什么加这条） | ≤ 200 字符 |
| `meta.createdAt` / `updatedAt` | number | 是 | 自动 | 审计与排序 tie-break | — |

**关键取舍说明**

- **不保留 `type` + `proxyMode` + 前缀/目标四字段的旧结构**。旧模型的问题正是"类型 + 模式 + 两个目标字段"组合出 2×2 语义，其中一半组合非法（mock + fullUrl 无意义）。新模型用单一 `action.kind` 表达，字段只在对应 kind 下出现。
- **`order` 即优先级**：列表可拖拽，内部换算成 DNR priority（见 4.4）。不暴露裸数字 `priority` 给普通用户，避免"数字越大越优先"的认知负担；高级面板可看只读值。
- **`match.host` 与 `match.path` 分开**，不再拼成 `urlFilter` 字符串，从根上消除"host 里带路径"的歧义。
- **`headers` 是 `action` 的可选子对象，不是独立规则类型。** 这样"转发 + 换 token"仍然是一条用户规则、一个 `order`、一个开关；DNR 侧的拆分是实现细节（见 4.9.2）。`headers-only` 只是为了让"只改头不改向"不必用"目标=源"来伪造，不是另起一套。

### 4.4 匹配语义、优先级与冲突解决

**匹配算法（面板/配置页本地模拟器与编译器共用同一份实现）**

1. 取请求 URL 的 `scheme`、`host`、`pathname`（不含 query），query 单独保存。
2. `scheme` 不匹配 → 不命中。
3. `host`：`*.example.com` 只匹配子域（`a.example.com`），**不匹配** `example.com` 本身（需要覆盖裸域时再加一条）；精确 host 做字符串相等。先把输入归一化：小写、去掉端口、去掉末尾点。
4. `path`：编译成锚定正则 `^/api/(.*)$` 或 `^/api$`；`caseSensitive` 默认 `true`。
5. `excludeHosts` / `excludeInitiator` 命中 → 直接排除。
6. 收集所有命中的 `enabled` 规则，按 `order` 从小到大取第一条（等价于 priority 从高到低）。
7. 若第一条是 `mock` → 由 mock 引擎处理（不编译 DNR）；若是 redirect → 生成目标 URL，并**再跑一次匹配**：若目标 URL 又命中同一规则（或形成 A→B→A 环）→ 该规则在保存时就被拒绝。

**优先级/冲突解决规则**

| 场景 | 处理 |
|---|---|
| 多条命中 | `order` 在前者生效（DNR 侧由唯一 priority 保证） |
| 两条规则匹配条件**完全相同**（同 scheme/host/path/resourceTypes） | 保存时**阻止**，提示"与第 3 条规则完全重复" |
| 包含关系（`/api/*` 与 `/api/user`） | 保存时**警告**不阻止，提示"更具体的规则请放在前面" |
| 同 host 多条 + 不同动作 | 允许；列表内用分组显示，便于检查顺序 |
| 自环（目标再次命中自身） | 阻止，给出两条修复建议（加 excludedHosts / 改目标前缀） |
| 仅大小写不同的两条 | 视为不同规则，但提示"若关闭大小写敏感将与第 N 条冲突" |

**DNR 侧的唯一化**：编译时按 `order` 排序，`dnrPriority = 1_000_000 - index * 10`（严格递减、无并列）。这样即使 DNR 对同优先级有内部排序规则，也不会影响结果。规则 id 用 `1000 + index`，并把 `configId → dnrId` 写入 `storage.local` 的 `compiledMap`，SW 重启后仍能反查（解决 P-22、R-15）。

**请求头与 redirect 的关系**：请求头不参与"选哪条 redirect"的裁决，它属于另一个评估阶段；同一条用户规则的 redirect 部分与 header 部分共享同一个 priority，但各自在独立阶段生效。因此 priority 的唯一化只解决"同阶段内谁先应用"，不需要在 redirect 与 modifyHeaders 之间做取舍（详见 4.9.2、4.9.3）。

### 4.6 编译到 DNR（三种 redirect 形态的取舍）

| 形态 | 能表达什么 | 保留原 query | 可跨 host | 条件 | 代价/风险 | 本方案用途 |
|---|---|---|---|---|---|---|
| `redirect.url` | 整条 URL 替换 | 否（需自己拼） | 是 | 任意 condition | 目标必须绝对 http(s)；原 query 需手工拼 | `redirect-url` |
| `redirect.transform` | 按组件改写（scheme/host/port/path/query/fragment） | 是（不传 `query` 即保留；传空串即清空） | 是（可设 host） | 任意 condition | 只能整条替换 path，无法保留通配后缀 | `redirect-exact` |
| `redirect.regexSubstitution` | 用捕获组重建 URL | 是（`\1` 可含 `?query`） | 是（替换串可写任意 host） | **必须** `regexFilter` | RE2 语法；模式非法会导致整次规则更新失败；有总量/内存开销 | `redirect-prefix`（唯一能保留后缀的方式） |

**编译示例 1：前缀替换并保留 query（当前 `pathReplace` 想表达但没做到的效果）**

配置：host `192.168.1.100`，path `/demo/api/sessions/*`，目标前缀 `/proxy/api/sessions`，keepQuery `true`。

```json
{
  "id": 1000,
  "priority": 999990,
  "action": {
    "type": "redirect",
    "redirect": { "regexSubstitution": "https://192.168.1.100/proxy/api/sessions\\1" }
  },
  "condition": {
    "regexFilter": "^https?://192\\.168\\.1\\.100/demo/api/sessions(.*)$",
    "resourceTypes": ["xmlhttprequest", "other"]
  }
}
```

`/demo/api/sessions/123?a=1` → `https://192.168.1.100/proxy/api/sessions/123?a=1`（后缀与 query 都在 `\1` 里）。

**编译示例 2：精确替换并丢弃 query**

```json
{
  "id": 1001,
  "priority": 999980,
  "action": {
    "type": "redirect",
    "redirect": {
      "transform": {
        "scheme": "https",
        "host": "test.example.com",
        "path": "/v1/user",
        "query": ""
      }
    }
  },
  "condition": {
    "regexFilter": "^https?://192\\.168\\.1\\.100/v1/user(?:\\?.*)?$",
    "resourceTypes": ["xmlhttprequest", "other"]
  }
}
```

**编译约束**

1. **默认全部用 `regexFilter`**（规则规模中等，优先保证语义精确）。当规则数超过阈值（建议 200，可配）时提示切换到"兼容模式"（`urlFilter` 近似匹配，接受 `/api` 误命中 `/apix`），并在列表打"近似匹配"徽标。【待补充：regexFilter 规则数量/内存上限，见官方 Limits 一节】
2. `regexFilter` 必须做编译期验证（在页面侧用 `new RegExp` 预检 + 用 `chrome.declarativeNetRequest.testMatchOutcome` 抽查），**一条非法正则会导致整次 `updateDynamicRules` 失败**。
3. 每条配置在编译时校验生成的 JSON 是否满足 DNR schema（`Rule` 必填项、`id ≥ 1`、`priority ≥ 1`）。
4. **不生成 `websocket` 资源类型**（redirect 对 WS 无效，见 R-12）。
5. `http`/`https` 用 `^https?://` 统一表达，**不再生成两条规则**；规则数减半（解决 P-09、R-16）。
6. **含 `headers` 的用户规则会拆成 1–2 条 DNR 规则**（redirect + modifyHeaders），规则总量按 `redirect 数 + header 数` 估算，不是按用户规则数估算（见 4.9.2）。

**编译产物示例（可回显给用户看）**

```json
{ "id": 1000, "priority": 999990, "action": { "type": "redirect", "redirect": { "regexSubstitution": "…\\1" } },
  "condition": { "regexFilter": "^https?://…", "resourceTypes": ["xmlhttprequest","other"] } }
```

### 4.7 Mock：根因与方案结论

**根因（三层）**

1. **DNR 没有"合成响应"能力。** 它的 action 只有 `block / redirect / allow / allowAllRequests / upgradeScheme / modifyHeaders`，redirect 只能改请求目标，不能返回 body（`sw.js:13` 直接返回 null 是正确但残缺的处理）。
2. **`data:` / `blob:` 不是合法 redirect 目标**（只允许 http/https 或扩展内路径），所以"用 data URL 塞 JSON"这条路在协议层就被封死。
3. **redirect 到扩展内文件也不适合 API mock**：静态文件不能按请求动态生成 body，且跨源读取会受 CORS 约束。

**方案对比**

| 方案 | 能力 | 新增权限 | 落地成本 | 商店/安全风险 | 结论 |
|---|---|---|---|---|---|
| A. DNR redirect → `data:`/`blob:` | 无 | — | — | — | **不可行**（目标 scheme 不被允许） |
| B. DNR redirect → 扩展内静态文件 | 只能返回固定文件；MIME 固定；CORS 受限 | `web_accessible_resources` | 低 | 低 | 仅适合替换脚本/图片，不适合 API JSON |
| C. DNR redirect → 本地 mock server（`127.0.0.1`） | 任意状态码/头/体/延迟；覆盖所有资源类型 | 无（但要用户跑进程） | 中（要分发/启动一个本地服务） | 低（纯 redirect），但要处理端口、CORS、启动引导 | **P2 可选**，作为"高级模式" |
| D. `chrome.debugger` + `Fetch.fulfillRequest` | 全类型、最完整（可改响应、可拦 WS 握手） | `debugger` | 中 | **高**：强权限警告、黄条提示、与 DevTools 附着冲突、审核最严 | **不采用** |
| E. MAIN world 注入，patch `fetch` / `XMLHttpRequest` | 页面脚本发起的 fetch/XHR 可返回任意 body/status/延迟；**天然绕过 CORS 与预检**（请求根本没发出） | `scripting`（+ 用户授权 host） | 低（复用现有注入通道与规则模型） | 低–中（需说明注入范围；`eval` 形式要改） | **采用（v0.6 默认）** |
| F. `chrome.proxy` + PAC 指向本地代理 | 全流量、可做完整 MITM | `proxy` + 本地进程 + 证书 | 高 | 高（系统级代理、证书信任） | 不做 |
| G. `chrome.webRequest` 阻塞式改写 | 可返回自定义响应 | `webRequestBlocking` | — | — | **MV3 普通扩展不可用** |

**结论（明确）**

1. **v0.5 先把"假启用"修掉**：`type=mock` 在列表显示 `未生效（待实现）`，保存时给出说明，`manifest` 与商店文案删掉 Mock 承诺。这一步不写新功能，只是停止误导。
2. **v0.6 用方案 E 落地 Mock**，产品口径统一为：**"Mock 页面脚本发起的 fetch/XHR 响应"**。技术要点：
   - 用 `chrome.scripting.registerContentScripts` 注册 `world: "MAIN"`、`runAt: "document_start"` 的 `mock-inject.js`，**仅在存在 mock 规则时注册**，无规则时注销（最小足迹）。
   - MAIN world 拿不到 `chrome.storage`：由 ISOLATED world 的桥接脚本读取规则，通过 `window.postMessage`/`CustomEvent` 下发"编译后的 mock 表"，MAIN world 只做匹配与响应。
   - 匹配使用与 4.4 完全相同的匹配器（同一份纯函数，打包两份或由桥接下发编译结果，避免逻辑漂移）。
   - 返回 `new Response(body, {status, headers})`，`delayMs` 用 `setTimeout`；对 `Request` 入参、`signal`、`credentials` 做最小兼容。
   - 幂等安装：保存原生 `fetch`/`XHR` 引用，重复注入直接返回；页面自己 patch 时以"我们的在外层、可透传"为原则。
   - **mock 规则不编译进 DNR**（否则请求会先被网络栈改写，JS 层永远看不到），编译阶段显式分流并标注。
3. **方案 C 只作为 P2 可选**：当用户明确需要 mock `<img>`、iframe、Worker、Service Worker 内的请求时，提供"本地 Mock 服务 + 规则导出"（扩展不内置服务，只导出配置并提供启动说明）。默认关闭。
4. **永不默认采用 D**。即使企业内部分发也不建议，因为调试器附着会与用户自己的 DevTools 冲突。

**能力边界（必须写进 UI 与商店描述）**

| 覆盖 | 不覆盖 |
|---|---|
| 页面脚本里的 `fetch`、`XMLHttpRequest`（axios/jQuery 默认走 XHR） | `<img>`、`<script>`、`<link>`、iframe 导航、`sendBeacon`、`EventSource` |
| 跨域请求（拦截后不发出，天然无预检） | Worker / Service Worker 内的 fetch（不同全局环境） |
| 可自定义 status/headers/body/延迟 | 页面在注入前已发出的请求、页面自己缓存的结果 |

### 4.7.1 v0.7 实现落地（权限路线 + 热更新 + 边界）

**权限路线**：默认走 A（`scripting.registerContentScripts`），因为它能让 Mock 在日常页面生效；B（DevTools 面板注入）只作为降级。新增 `scripting` 权限，但注册只发生在用户已授权的 host 上，未授权域名不注入；没有启用的 Mock 规则时注销全部脚本。`scripting` 不产生安装期“读取所有网站数据”提示，justification 见 `上架与合规.md` 3.4。

**文件职责**

| 文件 | world | 职责 |
|---|---|---|
| `mock-bridge.js` | ISOLATED | 读 `storage.local.proxyRules`，用 `RuleModel.buildMockTable` 生成最小表，`postMessage` 下发；订阅 `storage.onChanged` 做热更新；响应 MAIN 的 `hello` 请求 |
| `mock-inject.js` | MAIN | 只在表非空时安装 fetch/XHR 钩子；命中则构造响应，未命中调用保存的原生实现；表空/关闭时还原原生 |
| `rules-model.js` | 两个 world 共用 | 唯一匹配/归一实现：`matchRule`、`selectMockRule`、`normalizeMock`、`buildMockTable` |
| `sw.js` | service worker | 按已授权 host 计算 `matches`、注册/注销两个内容脚本，结果写入 `proxySyncStatus.mockRegistered/mockRegistrationError` |

**热更新**：options/popup 写 `storage.local` → `storage.onChanged` → 桥接重新生成表 → `postMessage` → MAIN 重新装载或还原。已注入页面无需刷新。开关关闭（最后一条 Mock 规则禁用/删除/域名撤销）时桥接下发空表，MAIN 立即还原 `window.fetch` 与 `XMLHttpRequest.prototype.open/send/abort`。

**匹配与优先级**：按规则 `order` 升序，命中第一条即返回；host/path/scheme/excludeHosts/大小写语义与 DNR 编译共用 `matchRule`，不维护第二套。Mock 不进入 DNR 编译。

**延迟语义**：`delayMs` 在 fetch 路径上可被 `AbortSignal` 中断（中断返回 `AbortError`）；同步 XHR（`async=false`）忽略延迟，立即返回；异步 XHR 延迟期间调用 `abort()` 会清定时器并触发 `abort`/`loadend`。

**未命中透传**：fetch 直接 `origFetch.apply(this, arguments)`，不改入参、不包 Response、不碰 signal/streaming；XHR 直接调用原生 `send`。页面在钩子之后再次 patch 时，以页面外层为优先，调用链仍可透传。

**已知覆盖不到**（UI 与文案已写明）：`<img>`/`<script src>`/`<link>` 等资源加载、iframe 内部、Worker/Service Worker 全局、WebSocket 握手、`sendBeacon`（fire-and-forget，无可读响应）；注入前已发出的请求；授权新域名后已打开的页面（需要刷新或面板注入才会带上新 host）。

### 4.9 HTTP 请求头配置（并入规则模型）

> 能力定位：给"接口联调"补上最后一环——把测试环境的鉴权头、灰度头、调试头随规则一起切换，避免每换一个环境就手工改 token。**只做 HTTP(S) 请求头；不做 WebSocket 握手头；v1 不做响应头。**

#### 4.9.1 规则模型：`headers` 挂在 `action` 下

```json
{
  "action": {
    "kind": "redirect-prefix",
    "targetPath": "/proxy/api",
    "keepQuery": true,
    "headers": [
      { "op": "set",    "name": "Authorization",   "value": "Bearer test-token" },
      { "op": "remove", "name": "X-Legacy-Trace" },
      { "op": "append", "name": "X-Forwarded-For", "value": "10.0.0.1" }
    ]
  }
}
```

字段约束：

- `op`：`set` / `append` / `remove`。
- `name`：符合 RFC 7230 token；大小写不敏感；保存前 trim。
- `value`：`set`/`append` 必填；`remove` 必须为空；不含 CR/LF；单值 ≤ 4KB。
- `headers`：单规则 ≤ 16 条；序列化后总大小 ≤ 8KB。
- 同一规则内头名不得重复（大小写不敏感）；需要多次追加时拆到不同规则（叠加限制见 4.9.3 H-5），**不要用逗号手工合并**（`Cookie` 等头的分隔符不是逗号）。
- **不做变量插值**（不引入 `{{token}}` 模板）：避免第二套求值引擎与"值从哪来"的隐私问题。

**与 `action.kind` 的组合关系**

| kind | 允许 `headers` | 编译结果 | 说明 |
|---|---|---|---|
| `redirect-exact` | 是 | redirect 规则 + modifyHeaders 规则 | 改向 + 改头 |
| `redirect-prefix` | 是 | 同上 | 最常用：切测试环境 + 换 token |
| `redirect-url` | 是 | 同上 | 跨 host 时注意目标 host 权限（4.9.9） |
| `mock` | **否** | 不编译 | 请求根本不发出，改请求头无意义；响应头用 `action.mock.headers` |
| `headers-only`（新增） | 是（至少 1 条） | 仅 modifyHeaders 规则 | 只改头不改向，避免用户用"目标=源"来伪造 |

保存时若 `kind: "mock"` 且 `headers.length > 0` → 直接报错，并提供一键"移到 Mock 响应头"。理由：v0.6 的 mock 由 MAIN world 的 `fetch`/`XHR` 拦截器接管，请求不进入网络栈，DNR 的 `modifyHeaders` 没有作用对象。

#### 4.9.2 编译到 DNR：拆成 1–2 条规则

**为什么必须拆**：DNR 的 `action.type` 是单值枚举（`block` / `redirect` / `allow` / `upgradeScheme` / `modifyHeaders` / `allowAllRequests`），一条 DNR 规则不可能同时是 redirect 和 modifyHeaders。来源：Chrome 官方 Reference 的 `RuleAction` 与 MDN `RuleAction.type`（文档确认）。

**id 分配**：索引 `i` = 已启用、可编译规则按 `order` 排序后的下标（mock/disabled 不占位）。

| 部分 | DNR id | 生成条件 |
|---|---|---|
| redirect | `1000 + i` | `kind` ∈ `redirect-*` |
| 请求头 | `2000 + i` | `headers.length > 0` 且 `kind ≠ mock` |

- 上限 250 条用户规则 → redirect 占 1000–1249、headers 占 2000–2249，区间不重叠。
- 反查：`id ∈ [1000,2000)` → 第 `id-1000` 条规则的 redirect 部分；`id ∈ [2000,3000)` → headers 部分。`compiledMap` 写成 `{ [dnrId]: { ruleId, part: "redirect" | "headers" } }`。
- 重排会改变 `i`，因此 id 不稳定；`compiledMap` 每次全量重建，`updateDynamicRules` 用 `getDynamicRules()` 求差集删除旧 id（现有 `sw.js` 已是这个模式）。

**priority**：两部分使用**同一个** priority。

```
priority(i) = 1_000_000 - i * 10
```

- redirect 与 modifyHeaders 在**不同阶段**裁决，不互相竞争，同 priority 不会冲突；
- 在各自阶段内，每个 `i` 的 priority 严格递减且唯一，满足"列表顺序即优先级"；
- 250 条时最小 priority 为 997,510，仍 ≥ 1。

**编译示例**：order=0，host `api.example.com`，path `/v1/*`，目标 `/test/v1`，3 个请求头。

```json
[
  {
    "id": 1000,
    "priority": 1000000,
    "action": {
      "type": "redirect",
      "redirect": { "regexSubstitution": "https://api.example.com/test/v1\\1" }
    },
    "condition": {
      "regexFilter": "^https?://api\\.example\\.com/v1(.*)$",
      "resourceTypes": ["xmlhttprequest", "other"]
    }
  },
  {
    "id": 2000,
    "priority": 1000000,
    "action": {
      "type": "modifyHeaders",
      "requestHeaders": [
        { "header": "Authorization", "operation": "set", "value": "Bearer test-token" },
        { "header": "X-Legacy-Trace", "operation": "remove" },
        { "header": "X-Forwarded-For", "operation": "append", "value": "10.0.0.1" }
      ]
    },
    "condition": {
      "regexFilter": "^https?://api\\.example\\.com/v1(.*)$",
      "resourceTypes": ["xmlhttprequest", "other"]
    }
  }
]
```

注意：

- `append` 只对 Chrome 白名单头可用（H-10）；示例用白名单内的 `X-Forwarded-For`。`X-Debug-Client` 这类自定义头 append 会被校验拦截，应改用 `set`。
- 两条规则的 `condition` 必须**完全一致**，否则会出现"改了头但没改向"或反之的错觉。
- `resourceTypes` 若含 `websocket`，headers 规则必须剔除该项；剔除后为空则跳过 headers 部分，并在列表打 `WS 不生效` 徽标（见 4.9.5 B-1）。

**规则总量与失败隔离**：每条带头的规则占 2 个 DNR 规则槽，UI 上限改为"编译后 DNR 规则 ≤ 500"（具体值以 `MAX_NUMBER_OF_DYNAMIC_RULES` 为准，【待查官方文档】），到 400 时提示"接近上限，建议合并规则"。若某条 header 规则仍被 Chrome 拒绝，沿用 `sw.js` 的"先整批、失败后逐条 add"策略；同一条用户规则的两部分会分别成败，列表必须能显示"转发已生效 / 请求头未生效"，不能合并成一个状态。

#### 4.9.3 裁决结论（逐条核对官方文档）

**先给结论**：

1. `redirect` 与 `modifyHeaders` **不是互斥择一**；它们在不同阶段生效，可以同时命中、同时生效。
2. 同一阶段内（尤其多条 `modifyHeaders` 改同一头）顺序由 priority 决定；高 priority 先应用，低 priority 受叠加规则限制。
3. 响应头能力必须分两件事：**改响应头（`RuleAction.responseHeaders`）Chrome 86+**；**用响应头作为匹配条件（`RuleCondition.responseHeaders`）Chrome 128+**。
4. Chrome 的 DNR 文档**没有给出"禁止修改的请求头"清单**，只有 append 白名单是明确的。`Host` / `Content-Length` / `Origin` / `Cookie` 的最终行为需实测，UI 先按保守策略。

**逐条来源**：

| # | 问题 | 结论 | 来源与原文 | 置信度 |
|---|---|---|---|---|
| H-1 | 一条 DNR 规则能否同时 redirect 和 modifyHeaders | 不能，`action.type` 是单值 | Chrome Reference `RuleAction`；MDN `RuleAction.type` 枚举 | 文档确认 |
| H-2 | 两者同时命中谁赢 | 不竞争：redirect 在 "Before the request" 阶段选候选；modifyHeaders 不在该阶段 | Chrome Reference *Rule evaluation → Before the request*：原文 "Rules with a `modifyHeaders` action are not included here as they will be handled later." | 文档确认 |
| H-3 | modifyHeaders 何时应用 | 请求头发出前；同扩展内高 priority 先应用 | Chrome Reference *Before request headers are sent*：原文 "Before Chrome sends request headers to the server, the headers are updated based on matching `modifyHeaders` rules." | 文档确认 |
| H-4 | 同 action 同 priority 的执行顺序 | 未标准化，可能随运行/浏览器版本变化 | Chrome Reference *Caution*：原文 "Browser vendors have agreed not to standardize the order in which rules with the same action and priority run." | 文档确认（因此本项目强制唯一 priority） |
| H-5 | 多条 modifyHeaders 改同一头 | append 后低优先级只能 append；set 后同扩展低优先级只能 append；remove 后低优先级不能再改 | Chrome Reference 同节三条 bullet；MDN `ModifyHeaderInfo` 同文 | 文档确认 |
| H-6 | redirect 后头规则匹配的是原 URL 还是新 URL | 官方未说明 | Chrome Reference 未定义；需实验 E-01 | **需实测** |
| H-7 | redirect 后 append 会不会重复追加 | 官方未说明 | 需实验 E-02 | **需实测** |
| H-8 | 改请求头/响应头的版本 | `RuleAction.requestHeaders` / `responseHeaders` 均 Chrome 86+ | MDN `RuleAction` 兼容表：requestHeaders Chrome 86、responseHeaders Chrome 86（Edge 86） | 文档确认 |
| H-9 | `responseHeaders` 是否 128+ 才支持 | 分两种：**动作**是 86+；**作为 condition** 是 128+ | MDN `RuleCondition` 兼容表：`responseHeaders` Chrome 128、Edge 128；Firefox 不支持 | 文档确认 |
| H-10 | append 支持哪些头 | Chrome 仅支持 21 个请求头（见下方清单） | MDN `ModifyHeaderInfo` *Header limits* | 文档确认 |
| H-11 | `Host` 能不能改 | Fetch 层禁止；webRequest 的 `onBeforeSendHeaders` 也不提供 Host；DNR 未给清单 | MDN Forbidden request header；Chrome webRequest 文档 "not provided to onBeforeSendHeaders"；DNR 无对应条目 → E-03 | **间接证据 + 需实测** |
| H-12 | `Cookie` 能不能改 | `append` 明确支持；`set`/`remove` 未确认 | MDN append 白名单含 Cookie；Chrome webRequest 文档称 Cookie 需 `extraHeaders` 才能改/删（webRequest 语境，非 DNR） | **部分文档确认 + 需实测** |
| H-13 | `Content-Length` 能不能改 | 不建议改；由网络栈计算，改后可能与实际 body 不一致 | Chrome webRequest 文档列 Content-Length 为不提供给 `onBeforeSendHeaders`；DNR 未定义 → E-03 | **间接证据 + 产品禁用** |
| H-14 | `Origin` 能不能改 | webRequest 需 `extraHeaders`；DNR 未定义；改它通常破坏 CORS | Chrome webRequest 文档原文："Starting from Chrome 79 ... Origin ... cannot be modified or removed without specifying 'extraHeaders'"；DNR 未定义 → E-03 | **间接证据 + 产品禁用** |
| H-15 | 带 `responseHeaders` condition 的 block/redirect | 请求已发出，无法真正阻止；block 让页面收到被阻止响应，redirect 会再发一次请求 | Chrome Reference *Once a response is received*：原文 "the request has already been sent to the server ... cannot actually block or redirect the request." | 文档确认（v1 不使用） |

**H-10 的 append 白名单（Chrome，21 个请求头）**：

`Accept`、`Accept-Encoding`、`Accept-Language`、`Access-Control-Request-Headers`、`Cache-Control`、`Connection`、`Content-Language`、`Cookie`、`Forwarded`、`If-Match`、`If-None-Match`、`Keep-Alive`、`Range`、`Te`、`Trailer`、`Transfer-Encoding`、`Upgrade`、`User-Agent`、`Via`、`Want-Digest`、`X-Forwarded-For`。

**关键原文（便于复核）**：

> "Rules with a `modifyHeaders` action are not included here as they will be handled later." —— Chrome Reference, Rule evaluation / Before the request

> "Before Chrome sends request headers to the server, the headers are updated based on matching `modifyHeaders` rules." —— Chrome Reference, Rule evaluation / Before request headers are sent

> "If a rule sets a header, then only lower priority rules from the same extension can append to that header. No other modifications are allowed." —— Chrome Reference, Rule evaluation / Before request headers are sent

#### 4.9.4 同时命中时的实际行为

| 场景 | 实际行为 | 依据 |
|---|---|---|
| 只有 redirect | 请求改向；头不变 | 文档 |
| 只有 headers（`headers-only`） | 请求原样发出；头按规则改 | 文档 |
| 同一用户规则：redirect + headers | 两条 DNR 规则都命中；先决定改向，再在发头前改头；**两者都生效** | H-2 / H-3 文档确认 |
| redirect 跨 host + headers | 头规则 condition 仍写原 URL；若浏览器在重定向后按新 URL 重新匹配，头不会生效；若按原 URL 匹配，则生效 | **H-6 需实测**，这是 v1 最大不确定点 |
| 两条规则改同名头 | 高 priority（列表靠前）先应用；后面的 `set`/`remove` 被忽略，`append` 可叠加（同扩展） | H-5 文档确认 |
| 低 priority 规则命中 `allow` / `allowAllRequests` | priority 低于或等于 allow 的 modifyHeaders 被忽略 | 文档确认 |
| 头名非法 / append 非白名单 | 编译期拦截；若漏网可能整条 DNR 规则被拒，靠失败隔离兜底 | 本项目策略 |
| `kind: mock` + headers | 保存时拒绝；不产生任何 DNR 规则 | 本项目策略 |

**UI 文案约束**：

- 列表行不要写"请求头已生效"这种绝对表述；用"已提交"并在帮助里说明"跨域重定向后是否作用到新地址需实测"。
- 跨 host 重定向（`redirect-url` 或 `redirect-exact` 改了 host）时，行内提示"跨域重定向后请求头可能不生效，请同时授权目标域名"。

#### 4.9.5 能力边界（三条，写进 UI 与商店描述）

| # | 边界 | 具体表现 | UI 提示 |
|---|---|---|---|
| B-1 | **只对 HTTP(S) 生效；WebSocket 握手头不能配** | `new WebSocket()` 不支持自定义头；DNR 对 `websocket` 握手的 `modifyHeaders` 行为官方未承诺，产品不依赖 | 编辑器固定提示："请求头仅对 HTTP(S) 请求生效；WebSocket 握手头无法修改。" 规则的 `resourceTypes` 含 `websocket` 时，行内再加 `WS 不生效` |
| B-2 | **跨域加自定义头会触发 CORS 预检，可能 403** | 加 `Authorization`/自定义头 → 浏览器发 OPTIONS；服务端未放行则失败；简单请求（GET/HEAD/POST + 简单头 + 简单 `Content-Type`）不触发 | 保存时若目标跨域且含非简单头，提示"目标服务需允许 OPTIONS 与对应头，否则会 403（这是预期行为）" |
| B-3 | **只改请求头，不读改请求体；v1 不做响应头** | 条件只能基于 URL/资源类型/请求方法等元数据，不能按 body 内容匹配；响应头留给 v1.1（动作 Chrome 86+，条件匹配 Chrome 128+） | 编辑器底部说明；不提供"按响应状态改头"的入口 |

补充：B-1 的产品口径是"不承诺"，不是"技术上绝对不可能"。若 E-04 实测发现 DNR 能改 WS 握手头，也不把它变成正式能力，避免依赖未文档化行为（浏览器升级即失效）。

#### 4.9.6 安全：头里通常有 token

| 风险 | 现状/设计 | 处理 |
|---|---|---|
| 本地存储 | `chrome.storage.local` 是**明文**（扩展配置目录下的 LevelDB，不加密）；不要用 `storage.sync`（会同步到云端） | 只存 `local`；写明"规则里的 token 以明文保存在本机"；提供"清除所有规则" |
| 列表展示 | 列表行会显示头名 | 敏感头值默认遮蔽为 `****`，点眼睛才显示；列表行只显示"N 个请求头"，不展开值 |
| 导出规则 JSON | 默认会带 `headers` | **默认脱敏**（4.8）；导出对话框有"包含敏感头原值"开关，勾选需二次确认并显示"将导出 N 个敏感值" |
| 导入 | 可能带入脱敏占位 | 检测 `__REDACTED__`，提示"该文件含脱敏值，导入后需手动补全"，不静默当真实值 |
| 抓包导出 | 不含请求头/握手头 | 钩子只记录 WS 帧，导出 schema 无 header 字段（7.1 明确） |
| 日志/错误上报 | 无 | 同步错误 `lastSyncError` 可能含头名，但不含值；仍只存本地 |
| 截图/共享 | 编辑器可见值 | 敏感头默认遮蔽；提供"隐藏所有值"开关 |

**建议放在设置页的文案**："请求头可能包含访问令牌。它们只保存在本机浏览器配置中（明文），不会上传。导出规则时默认脱敏；如需分享原值，请自行确认接收方可信。"

#### 4.9.7 UI 变更（popup 编辑区）

**编辑区新增"请求头"分组**

- 表头：操作 / 头名 / 值 / 删除。
- 操作下拉：`设置（set）` / `追加（append）` / `删除（remove）`。
- 头名：失焦即校验；重复名、禁用名给红边 + inline 文案。
- 值：`remove` 时禁用并清空；敏感头默认 `type=password` + 眼睛切换。
- 底部：`+ 添加请求头`，右侧计数 `3 / 16`。
- 固定提示（不折叠）："仅对 HTTP(S) 生效；WebSocket 握手头无法修改。跨域请求加自定义头会触发预检，服务端未放行时会 403。"
- `kind=mock` 时整个分组禁用，显示"Mock 请求不会发出，请到 Mock 响应头配置"。
- 空态："还没有请求头。常用：Authorization、X-Request-Id、X-Env。"

**列表行**

- 目标/路径行尾加徽标 `3 个请求头`（hover 只显示头名，值遮蔽）。
- 未授权域名：保留现有"待授权" +【授权此域名】，徽标旁加"未授权，请求头同样不生效"。
- `resourceTypes` 含 `websocket`：显示 `WS 不生效`。
- 同步失败：显示 `请求头未生效（编译失败）`，可展开看 `lastSyncError` 与具体头名。

**排序**：头行顺序不影响执行顺序（同名头已禁止），因此不做拖拽。

#### 4.9.8 校验规则（保存前纯函数）

头名合法性用 RFC 7230 token：

```js
const HEADER_NAME = /^[!#$%&'*+\-.^_`|~0-9A-Za-z]+$/;
```

| 校验 | 规则 | 文案 |
|---|---|---|
| 头名非空 | trim 后非空 | `头名不能为空` |
| 头名合法 | 匹配 `HEADER_NAME` | `头名只能包含字母、数字和 -_. 等 token 字符，不能有空格或冒号` |
| 重复头名 | 同规则内大小写不敏感唯一 | `「Authorization」重复了，请合并为一行` |
| 禁用头 | 见下方分级表 | `Host 由浏览器控制，不能通过此工具修改` |
| append 白名单 | 非白名单头禁止 append | `Chrome 只允许对白名单头使用 append；请改用「设置」或把多个值用逗号合并` |
| remove 带值 | `remove` 不允许 `value` | `删除操作不需要值` |
| set/append 空值 | 允许但警告 | `将发送空值头，部分服务端会拒绝` |
| 值含 CR/LF | 禁止 | `头值不能包含换行` |
| 单条长度 | ≤ 4KB | `单个头值过长（上限 4KB）` |
| 条数 | ≤ 16 / 规则 | `单条规则最多 16 个请求头` |
| 总大小 | ≤ 8KB / 规则 | `请求头总大小超限` |
| 跨规则同名 | 按 `order` 静态推演；低优先级 `set`/`remove` 会被忽略 | `第 5 条的「X-Env」不会生效：第 2 条已设置同名头，后面的规则只能追加` |

**禁用头分级（保守策略）**

| 头名 | 允许操作 | 依据 |
|---|---|---|
| `Host` | 禁止 | webRequest 文档：不提供给 `onBeforeSendHeaders`；DNR 未定义（H-11） |
| `Content-Length` | 禁止 | 网络栈计算；webRequest 文档同上（H-13） |
| `Origin` | 禁止 | webRequest 需 `extraHeaders` 才能改；改它破坏 CORS（H-14） |
| `Set-Cookie`（响应） | 禁止 | Fetch forbidden response header name；v1 不做响应头 |
| `Connection` / `TE` / `Trailer` / `Transfer-Encoding` / `Upgrade` / `Keep-Alive` | 禁止 | hop-by-hop，改了会破坏连接；虽在 append 白名单内，产品仍禁用 |
| `Sec-*` / `Proxy-*` / `Access-Control-Request-*` | 禁止 | Fetch forbidden header；安全敏感 |
| `Cookie` | 仅 `append` 允许；`set`/`remove` 需"高级"二次确认 | append 在 Chrome 白名单（文档确认）；set/remove DNR 未确认（H-12） |
| `Authorization` / `Proxy-Authorization` | 允许，强制敏感标记 | 调试令牌的核心场景；导出默认脱敏 |
| 其他 `X-*` / 自定义 | 全部允许 | 常规 |

> 说明：`Cookie` 的 `set`/`remove` 放进"高级"而不是完全禁止，是因为"删掉测试环境的 Cookie"是真实需求；保存时弹确认，并在列表标"需实测"。
>
> `Authorization` 虽然允许配置，但它在 Chrome webRequest 的 `onBeforeSendHeaders` 中属于"不提供"的头（见 12.2 的 webRequest 文档），DNR 能否修改它需在 E-03 中一并验证；若实测不生效，"换 token"可退化为自定义头（如 `X-Token`）或走测试网关。

#### 4.9.9 与权限、同步的衔接

- `modifyHeaders` 与 `redirect` 一样要求 **request URL 与 initiator 的 host 权限**。来源：MDN `RuleAction` 原文 "The use of the `redirect` and `modifyHeaders` actions require host permissions for the request and request initiator." → 未授权时头规则同样不能提交，`skippedNoPermission` 要把两部分都算上。
- 跨 host 重定向时，若只授权了源 host，重定向后的目标 host 可能无权限，头规则会被忽略（推断，需 E-06）。当前授权按钮只请求规则（源）host；目标 host 不同时需用户为其再建规则/授权（v0.7 已移除 `activeTab`，不自动纳入当前调试页）。
- 同步状态扩展为按部分计数，避免把"转发成功、请求头失败"合并成一个"已生效"：

```json
{
  "applied": { "redirect": 12, "headers": 9 },
  "skipped": { "noPermission": 3, "noHeadersKind": 0 },
  "lastSyncError": null
}
```

## 5. 模块 C：抓包面板重设计

### 5.1 先修数据通路（真正决定"几百条连接是否可用"）

现状账（`devtools-panel.js:32-42`、`118`）：

- 每 800ms 执行一次 `JSON.stringify({frames: 全部, connections: 全部})`；
- 上限 2000 帧 × 单帧 8000 字符（`ws-hook-source.js:11-12`）≈ **16M 字符/次**（中文 UTF-8 可到 40MB+），2000 个对象反复序列化；
- 页面主线程被占用，回传结果过大时 `inspectedWindow.eval` 可能失败或截断；
- 新增帧通常只有几条，**99% 的传输是重复数据**。

**改法**

1. **页面侧暴露增量读接口**（钩子内实现，v3）：
   ```js
   window.__WS_READ__ = function (sinceSeq, maxFrames) {
     // 从环形缓冲中取 seq > sinceSeq 的帧，附带连接元信息，返回 JSON 字符串
   };
   ```
   面板 `eval` 时只传 `sinceSeq`，单次回传降到"新增帧"级别（典型 < 20KB）。
2. **自适应轮询**：有新增 → 200ms；连续 5 次无新增 → 500ms；面板不可见 → 暂停（`document.visibilityState`）。
3. **渲染与数据解耦**：面板维护 `connModel` / `frameModel`，DOM 只是视口窗口；追加走 `requestAnimationFrame` 批量合并，避免每帧一次 reflow。
4. **面板侧同样设上限**，防止二次膨胀（与页面 2000 帧 / 8MB 对齐）。

### 5.2 布局：放弃"每连接一个 `<details>`"，改主从（master-detail）

现状 `details.open = true`（`devtools-panel.js:59`）导致所有连接全展开，几十条时既找不到目标，也无法比较。新布局：


**窄面板（DevTools 常被拖到很窄，< 700px）**：退化为上下分栏（列表 40% + 详情 60%），或"列表 → 点击进入详情"的两级页面，保证 320px 宽仍可用。

### 5.3 连接列表：导航与筛选

| 能力 | 设计 | 理由 |
|---|---|---|
| 固定头部 | 工具栏 + 列头 `position: sticky` | 滚动时不丢上下文 |
| 搜索 | 单一输入框，默认搜 URL；切换"搜消息内容"时仅搜当前连接（全量搜 payload 代价高，需显式确认） | 避免每次输入都全表扫描 2000 帧 |
| host 过滤 | 下拉，聚合当前连接集合的 host 并带计数（`api.example.com (12)`） | 一次点击缩小到目标域 |
| 只看有消息 | 开关，默认**开**：隐藏只有 `open`/`close` 生命周期的连接 | 几百条连接里大量空连接是主要噪音 |
| 状态过滤 | `OPEN` / `CLOSED` / `ORPHAN`（页面卸载） / `STALE`（长期空闲） | 排查断连时先看 ORPHAN |
| 排序 | 默认"最近活动倒序"；可切"开始时间 / 帧数 / URL" | 新连接优先出现在视野内 |
| 固定（pin） | 最多 3 条置顶，置顶区与普通区有分隔线 | 对比与持续观察 |
| 虚拟滚动 | 连接 > 50 条启用，DOM 节点恒定 ~30 | 几百条连接必须 |
| 行内容 | 状态点 + `ws-12` + URL（**省略中段**，保留 host 与 path 尾部）+ 帧数 + 时长/状态 | 长 URL 省略中段比截断尾部更能识别 |
| 悬停 | `title` 显示完整 URL；不弹浮层（浮层容易遮挡） | 低成本查看 |

**展开策略**：不再"全部展开"。选中连接即渲染详情；默认自动选中**最新一条**；用户手动选中后不再自动切换（有新帧也不抢焦点），只在列表行上显示未读帧计数徽标。

### 5.4 帧表格：列与截断

| 列 | 宽 | 内容 | 截断策略 |
|---|---|---|---|
| `#` | 48px | 帧序号 `seq`（真实序号，丢帧会出现空洞） | 不截断；空洞用 `…` 行标注"丢弃 N 帧" |
| 时间 | 92px | 相对连接打开时间 `+1.234s`（等宽数字） | 不截断；绝对时间在详情里 |
| 方向 | 56px | `in` / `out` / `open` / `close` / `error`（文字，左侧 2px 色条） | 不截断 |
| 类型 | 56px | `text` / `binary` | 不截断 |
| 大小 | 64px | 原始字节数（右对齐） | 不截断 |
| 预览 | flex | 单行，最多 120 字符，超出 CSS 省略号 | 不换行、不撑高；完整内容在详情面板 |

- 行高 24px，等宽字体 12px，斑马纹用极浅底色，**不用横线**（横线会让 2000 行变成"表格墙"）。
- 点击行 → 详情面板；双击行 → 复制 payload；`Enter` 打开详情；↑/↓ 移动。
- 新帧到达：若"跟随"开启且当前在底部 → 滚到底；否则在底部显示浮动条 `已暂停 · 12 条新帧 ↓`。

### 5.5 大 payload

| 场景 | 处理 |
|---|---|
| 1KB–100KB | 详情面板 `<pre>` 换行渲染；JSON 默认 pretty（懒解析，只在展开时 `JSON.parse` + `stringify`） |
| > 100KB | 只渲染前 2000 行 + "继续加载"按钮；查找用浏览器原生 `Ctrl+F` 会失效，改为面板内搜索并高亮前 500 命中 |
| 被截断（存储侧） | 必须显示 `已截断：保留前 4,096 字符，原始 123,456 字符`，并提供"该帧被截断"徽标 |
| 二进制 | 显示 `binary · N bytes` + 前 32 字节 hex；不尝试解码 |
| 复制 | 提供 `复制原始` / `复制格式化` 两个动作；后者失败时回退原文 |

### 5.6 暂停自动滚动

- 工具栏一个明确的 `跟随` 开关（默认开，但**不是强制**）。
- 用户向上滚动超过 8px → 自动关闭跟随（而不是每次都把人拽回去），底部出现 `已暂停 · 12 条新帧 ↓`。
- 点击浮动条或按 `End` → 恢复跟随并滚到底。
- 跟随关闭期间仍继续接收与计数，不清空、不丢帧。

### 5.7 多连接对比

| 阶段 | 方案 |
|---|---|
| v1（P1） | 选中 2–3 条连接 → `对比` 视图：按时间合并成一张表，列为"时间 / 连接 / 方向 / 预览"，每连接一色仅用左侧 2px 竖条区分；支持只显示 `in` 或只显示 `out` |
| v2（P2） | 时间轴泳道：每个连接一条水平线，帧为刻度，可缩放；用 canvas 绘制，避免大量 DOM |

**不做**：把多条连接"合并成一条流"再导出（会破坏 `connId` 语义），对比只在视图层做。

### 5.8 导出入口

| 位置 | 动作 |
|---|---|
| 工具栏右侧主按钮 `导出 ▾` | 全部连接 / 仅当前连接 / 选中连接 / 仅含错误的连接 |
| 详情头部 | `导出此连接`（最常用） |
| 导出前 | 显示预估体积 + 三个选项：`格式化 JSON`（默认关）、`包含 payload`（默认开）、`按连接拆分文件`（> 8MB 时默认开） |

### 5.9 注入时机（最影响"抓不到"的体验）

现状：面板打开才注入（`devtools-panel.js:24-30`），导航后固定等 500ms（`devtools-panel.js:203`）。

改法：

1. **改为 `document_start` 注入**：用 `chrome.scripting.registerContentScripts` 注册 `runAt: "document_start"`、`world: "MAIN"` 的钩子，仅在扩展启用"WS 抓包"时注册。这样 page 首次 `new WebSocket()` 之前钩子已就位，不再有 500ms 空窗。
2. 面板不再负责注入，只负责读取；面板关闭时钩子仍工作（内存上限不变），重新打开即恢复历史。
3. 页面导航由浏览器自动重新注入，无需 `onNavigated` 里 `setTimeout`。
4. **合规副作用**：不再需要 `fetch` + `eval` 源码字符串（`devtools-panel.js:24-30`），顺带解决 S-06。

## 6. 模块 D：WS 数据按链接分组的深化

### 6.1 现有实现已经做对的部分（不要回退）

- 按连接实例分组而不是按 URL 合并（`ws-hook-source.js:52-54`）：同 URL 并发连接不混淆。
- 单调 `seq` + 裁剪后按 seq 增量渲染（`devtools-panel.js:110-114`）：避免用数组下标。
- 导出保留 `direction` / `payload`（`devtools-panel.js:168-173`）：下游脚本可继续用。
- 帧总量按整页计而非按连接（`ws-hook-source.js:9-11` 的注释）：这个判断是对的。

### 6.2 缺口与改法

| 缺口 | 现状证据 | 影响 | 改法 |
|---|---|---|---|
| 跨页导航 | 面板 `resetView()`（`devtools-panel.js:98-100`），数据只保留当前页 | 多页流程（登录→跳转→业务页）只能抓最后一段 | 引入 `sessionId`（每次页面加载一个）+ 面板侧"会话切换"记录；导航时把上一会话归档到内存（上限 3 个），导出时可选择"包含历史会话" |
| 连接重名 | `ws-1` 每页重置（`ws-hook-source.js:54`） | 合并两份导出即撞 id | 保留 `id`（兼容），新增 `uid = sessionId + ":" + id`；导出以 `uid` 为真正主键 |
| 超时未关闭 | 无 `pagehide` 处理 | `closedAt` 永远 null，无法区分"活着"与"页面没了" | `pagehide`/`beforeunload` 时把所有 `open` 连接置 `status:"orphan"`、`closedAt:null`、`endedReason:"page_unload"`；面板对 >30s 无活动标 `空闲`，>5min 标 `STALE`（只改展示，不改数据） |
| 内存上限 | 2000 帧 / 8000 字符（`ws-hook-source.js:11-12`），全局 FIFO | 一条高频连接挤掉所有其它连接的早期帧 | 双上限：`maxFrames=2000` + `maxBytes=8MB`；按连接保底 20 帧；记录 `droppedFrames` 与 `droppedBeforeSeq` |
| 导出体积 | 全量 `JSON.stringify(..., null, 2)`（`devtools-panel.js:189`） | 8MB payload → 16MB+ 文件；浏览器内存翻倍 | 默认紧凑 JSON（大文件不缩进）；> 8MB 按连接拆分；提供"不含 payload"选项；估算体积后再导出 |
| 时间戳一致性 | `Date.now()`（`ws-hook-source.js:33`）+ `toLocaleTimeString()`（`devtools-panel.js:84`） | 墙钟跳变、跨机不可比、同秒不可排序 | 以 `performance.timeOrigin + performance.now()` 生成单调时间；导出同时给 `ts`（epoch ms，兼容）与 `t`（相对连接打开的 ms） |
| 单帧截断不可见 | `slice(0, MAX_PAYLOAD)`（`ws-hook-source.js:37`） | 下游误当完整报文 | 新增 `payloadTruncated` / `rawSize`；截断策略改为 head+tail 保留 |
| 二进制不可用 | `[binary]`（`ws-hook-source.js:74,79`） | binary 场景等于没抓 | 记录 `dataType` + `byteSize`；`Blob` 用 `size` 即可得长度（读内容成本高，默认不读）；可选"记录前 N 字节" |
| 无错误事件 | 只监听 open/close/message（`ws-hook-source.js:64-72`） | 断连原因缺失 | 监听 `error`，写 `direction:"error"`；`close` 补 `reason` / `wasClean` |
| 帧计数失真 | `conn.frameCount++` 只增不减（`ws-hook-source.js:39`） | 页面计数与缓冲不一致 | 拆成 `frameCount`（累计）与 `bufferedFrames`（当前保留），导出两者都给 |

### 6.3 页面侧数据结构（v3）

```js
window.__WS_SESSION__ = {
  version: 3,
  sessionId: "s-<random>",
  pageUrl: location.href,
  timeOrigin: performance.timeOrigin,
  startedAt: Math.round(performance.timeOrigin),
  limits: { maxFrames: 2000, maxBytes: 8388608, maxPayload: 4096, minPerConn: 20 },
  connections: [ /* 见下 */ ],
  frames: [ /* 环形缓冲 */ ],
  droppedFrames: 0
};
```

```js
// connection
{
  id: "ws-1",                    // 兼容旧字段：会话内唯一
  uid: "s-ab12:ws-1",            // 全局唯一
  url: "wss://api.example.com/chat",
  protocols: ["json"],
  openedAt: 1762329600000,       // epoch ms（单调时钟换算）
  closedAt: 1762329603120,
  closeCode: 1000,
  closeReason: "",
  wasClean: true,
  status: "closed",              // open | closed | orphan | stale(展示层派生)
  endedReason: null,             // page_unload | close_event | hook_disposed
  initiator: { scriptUrl, line },// 可选，采样 Error().stack，失败则 null
  frameCount: 128,               // 累计（含已丢弃）
  bufferedFrames: 120,           // 当前保留
  droppedFrames: 8,
  bytesIn: 10240,
  bytesOut: 2048,
  truncated: false,
  lastActivityAt: 1762329603120
}
```

```js
// frame
{
  seq: 42,                // 全局单调，裁剪后仍单调
  ts: 1762329601234,      // epoch ms（由单调时钟换算，不受墙钟回拨影响）
  t: 1234,                // 相对连接打开时间 ms
  connId: "ws-1",
  uid: "s-ab12:ws-1",
  direction: "in",        // open | in | out | close | error（保留旧值）
  dataType: "text",       // text | binary | blob
  byteSize: 128,
  payload: "...",         // 兼容旧字段：字符串
  rawSize: 128,           // 截断前长度
  payloadTruncated: false
}
```

**内存策略**

- 上限：`2000` 帧 且 `8MB`，先到先丢；每连接保底 `20` 帧（高频连接不能把其它连接挤空）。
- 单帧：`maxPayload = 4096` 字符；超出时保留 `head 2048 + tail 1024`，中间插 `…<省略 N 字符>…`，并置 `payloadTruncated`。
- 丢帧时维护 `conn.droppedFrames`、`conn.truncated`、全局 `droppedFrames`，并在帧流里留下"空洞位置"提示（导出侧用 `seq` 差值即可算）。

### 6.4 时间戳一致性

| 项 | 规则 |
|---|---|
| 采集 | `perfNow = performance.now()`；`ts = Math.round(timeOrigin + perfNow)`；同时保存 `perf` 原值（可选） |
| 相对时间 | `t = ts - conn.openedAt`（连接未 open 时以会话 `startedAt` 为基准，并标 `tBase: "session"`） |
| 展示 | 列表与表格用 `t`（`+1.234s`）；详情展示 `ts` 的本地时间带毫秒 + 时区 |
| 导出 | `timestamp` 为 ISO 8601 UTC（`Z`）；`ts` 为 epoch ms；两者必须一致（同源换算） |
| 跨会话 | 每个会话带 `timeOrigin` 与 `sessionId`；跨会话对比只能用 `ts`，不能用 `t` |

> **抓包导出不含 HTTP 请求头或 WebSocket 握手头**：钩子只记录帧数据，不读取 `Sec-WebSocket-*`、`Cookie`、`Authorization`。请求头配置只存在于规则导出（4.8），且默认脱敏。因此 WS 导出文件的隐私风险与请求头配置无关。

### 7.2 兼容性承诺（硬约束）

以下字段**必须存在且语义不变**，否则视为破坏性变更：

| 层级 | 字段 |
|---|---|
| 顶层 | `exportedAt`、`page` |
| 连接 | `id`、`url`、`openedAt`、`closedAt`、`closeCode`、`truncated`、`frameCount`、`frames` |
| 帧 | `direction`、`timestamp`、`ts`、`payload` |

新增字段只增不改；`direction` 的新值 `error` 属于**扩展值**，旧消费者按"未知方向"处理即可（建议下游用白名单而不是 `else` 兜底）。`schemaVersion` 从 `"2.0"` 起；旧文件（无 `schemaVersion`）按 v1 解析。

### 7.3 大数据与消费

| 场景 | 方案 |
|---|---|
| 单文件 > 8MB | 默认"按连接拆分"：`ws-.../ws-1.json`、`manifest.json`（含 `stats` 与索引） |
| 只需解析不需人工阅读 | 提供 NDJSON 选项：每行一个帧对象，带 `uid`/`seq`，便于 `jq`/脚本流式处理 |
| 体积预估 | 导出前按 `sum(byteSize)` × 系数（紧凑约 1.1、格式化约 2.0）估算并显示 |
| 检查完整性 | 每个连接输出 `returnedFrameCount + droppedFrames = frameCount` 的等式；导出侧自检失败则在 `stats.warnings` 中标注 |

**下游消费示例**

```bash
jq -r '.connections[] | "\(.url)\t\(.frameCount)\t\(.status)"' ws-*.json
jq -r '.connections[].frames[] | select(.direction=="in") | [.ts, .payload] | @tsv' ws-*.json
```

## 9. 风险

| 编号 | 风险 | 可能性 | 影响 | 缓解 |
|---|---|---|---|---|
| K-01 | `regexFilter` 模式非法 → 整次 `updateDynamicRules` 失败 | 中 | 全部规则失效 | 编译期 `new RegExp` 预检 + `testMatchOutcome` 抽查 + 逐条失败隔离 + 明确错误提示 |
| K-02 | `regexFilter` 规则过多触发 DNR 总量限制 | 中 | 后加的规则被拒 | 阈值提示 + 兼容模式（`urlFilter`）+ 规则合并建议【待补充：官方 Limits 具体值】 |
| K-03 | `requestDomains` 是否包含子域语义不明确 | 中 | host 误匹配 | **S0 先做验证实验**；若包含子域，则补 `excludedRequestDomains` 或回归 `\|scheme://host` 两条的写法 |
| K-04 | `optional_host_permissions` + 运行时授权能否满足 DNR redirect | 中 | 权限方案推翻重做 | S0 做一次 spike（授权前/后分别 `updateDynamicRules` 并实测 redirect）【待验证】 |
| K-05 | MAIN world 拦截与页面自身 patch 冲突 | 中 | mock 在某些站点失效 | 幂等安装、保留原生引用、失败时降级为"不拦截"并上报状态 |
| K-06 | 页面检测 `fetch` 被改写（指纹） | 低–中 | 少数站点风控 | 不伪造 `toString`（避免更严重的合规问题）；文档说明能力边界 |
| K-07 | 跨域重定向被 CORS / mixed content 拦截 | 高 | 用户以为工具坏了 | 文档 + UI 提示（https→http 禁止；凭据请求不能 `*`）；诊断器给出"可能失败原因" |
| K-08 | 提升 `main_frame` 权限后被恶意规则误用 | 低 | 站点打不开 | 默认关闭 + 二次确认 + 自环检测 + 一键全部停用 |
| K-09 | 面板增量协议改造引入丢帧 | 中 | 数据不完整 | `seq` 空洞检测 + 导出完整性等式自检 + 保留全量拉取作为兜底开关 |
| K-10 | 商店判定"单一用途"不合格 | 高 | 无法上架 | 重构定位为"接口联调辅助"，或拆成两个扩展（见 10.4） |
| K-11 | `<all_urls>` 或 `debugger` 触发深度审核 | 高 | 审核周期不可控 | 用可选主机权限 + 按需申请；绝不申请 `debugger` |
| K-12 | 注入方式被误判为远程代码 | 中 | 拒审 | 改为 `scripting.executeScript({files})` / 注册内容脚本，删除 `fetch + eval` |
| K-13 | 导出 schema 变更破坏下游脚本 | 中 | 用户脚本报错 | 兼容性硬约束（7.2）+ 版本号 + README 更新 |
| K-14 | 2000 帧上限对高频场景仍不够 | 高 | 数据缺失 | 显式 `droppedFrames` + 导出告警 + 可调上限（受内存上限约束） |
| K-15 | 无自动化测试导致回归 | 中 | 语义反复出错 | 为 `rules-model.js` 与编译函数建纯函数单测（Node 直接跑，不需要浏览器） |

### 10.4 针对"单一用途"的两种解法（需产品决策）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 统一叙事（推荐先试） | 定位为"**接口联调辅助工具**"：一个目的 = 让前端在本地把请求指向测试环境并核对 WebSocket 报文。代理与抓包都是"联调"的子能力，描述里用同一句话统领 | 一个包、维护成本低 | 仍可能被审核认为"两个功能"；需文案与截图都围绕同一场景 |
| B. 拆成两个扩展 | `api-redirect`（代理）与 `ws-capture`（抓包），共享 UI 规范 | 单一用途最干净，权限更小（抓包版不需要 `<all_urls>`） | 双份提审、双份素材、用户要装两个 |

**建议**：先按 A 提交；若被拒且理由明确指向单一用途，再执行 B（代码已是模块化边界，拆分成本可控）。

## 11. 验收标准

### 11.1 规则模型（编译层，必须可自动化验证）

| 用例 | 输入 | 期望 |
|---|---|---|
| T-01 前缀保留后缀 | host `192.168.1.100`，path `/api/*`，target `/proxy/api`，请求 `/api/123?a=1` | 重定向到 `/proxy/api/123?a=1` |
| T-02 路径边界 | path `/api`，请求 `/apix` | 不命中 |
| T-03 大小写 | path `/api`，请求 `/API` | 不命中（`caseSensitive: true`） |
| T-04 fullUrl 丢 query | target `http://t/x`，`keepQuery=false`，请求 `?a=1` | 目标无 `a=1` |
| T-05 优先级 | 两条都命中，`order` 分别为 1/2 | 第 1 条生效；编译后 priority 严格递减 |
| T-06 自环 | 目标再次命中自身 | 保存被拒，提示可操作 |
| T-07 非法前缀 | target 不以 `/` 开头 | 保存被拒，字段级错误 |
| T-08 mock 分流 | `kind: "mock"` | 不产生任何 DNR 规则；由 mock 引擎接管 |
| T-09 websocket | 任何规则 | 不生成 `websocket` 资源类型 |
| T-10 失败隔离 | 3 条规则，第 2 条非法 | 第 1、3 条仍生效，第 2 条标"应用失败" |
| T-11 子域通配 | host `*.example.com`，请求 `example.com` | 不命中；`a.example.com` 命中 |
| T-12 规则上限 | 超过上限 | 明确报错，不静默丢弃 |
| T-13 拆分编译 | 一条 redirect-prefix 规则带 2 个请求头 | 产出 2 条 DNR 规则：id `1000+i` / `2000+i`，priority 相同，`condition` 完全一致 |
| T-14 id 不碰撞 | 250 条规则，每条都带头 | redirect 1000–1249、headers 2000–2249，无重复、无越界 |
| T-15 headers-only | `kind` 为 `headers-only` | 只产出 `modifyHeaders` 规则，不产出 redirect |
| T-16 mock 禁头 | `kind: mock` + `headers` | 保存被拒，提示改用 Mock 响应头 |
| T-17 禁用头 | 头名 `Host` / `Content-Length` / `Origin` | 保存被拒，字段级错误 |
| T-18 append 白名单 | 对 `X-Debug-Client` 用 `append` | 保存被拒，提示改用 `set` |
| T-19 remove 带值 | `op: remove` 且 `value` 非空 | 保存被拒 |
| T-20 重复头名 | 同一规则内两次 `Authorization` | 保存被拒 |
| T-21 跨规则同名 | 第 1 条 `set X-Env`、第 2 条 `set X-Env` | 保存时警告"第 2 条不会生效"（依据 H-5） |
| T-22 导出脱敏 | 规则含 `Authorization: Bearer abc` | 默认导出为 `__REDACTED__`；勾选"原值"后才出现明文 |
| T-23 未授权过滤 | 规则域名未授权 | redirect 与 headers 两部分都不提交；`skipped.noPermission` 计数包含两者 |
| T-24 WS 边界 | 规则 `resourceTypes` 含 `websocket` | headers 规则剔除 `websocket`；若剔除后为空则不生成 headers 规则，列表显示 `WS 不生效` |

9. **E-01【必须实测】redirect 后 `modifyHeaders` 匹配的是原 URL 还是重定向后的 URL**：本地服务同时记录"请求到达的路径"与"收到的头"，规则用原 URL condition，观察头是否到达。
10. **E-02【必须实测】redirect 后 `append` 是否重复追加**：在重定向链上同时启用 redirect 与 append 规则，检查服务端收到的头行数/合并值。
